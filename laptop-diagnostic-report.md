### Новая проблема 1 — воспроизводимый GPU fault с 595

Сохранены две последовательные загрузки с одной и той же веткой 595:

- загрузка 11:35: в 11:36:48
  `nvidia-modeset: Idling display engine timed out`, затем в 11:38:49

- загрузка 11:41: в 11:42:06 ещё один `NVRM Xid 31`, снова процесс `Xorg` и

В сохранённых журналах с 14 июля до установки 595 `Xid 31` не встречался.
В NVIDIA-only-загрузке с 12:09 до итогового контроля в 13:25 новых Xid,
API mismatch и display-engine timeout нет. Это не доказывает дефект самого GPU:
последовательность гораздо больше похожа на несовместимость 595 с текущей
связкой ядра 7.0, Xorg, PRIME on-demand и перестройкой нескольких дисплеев.
Два одинаковых сбоя делают нестабильным именно проверенный режим PRIME
on-demand; текущий режим NVIDIA-only на подтверждённом интервале стабилен.

**Остаточное наблюдение:** в текущей загрузке есть 48 строк
`Failed to get memory pages for NvKmsKapiMemory`, сгруппированных во время
старта и перестройки дисплеев до 12:50:46. После 12:50:47 новых строк нет,
поэтому это не доказанная причина blackout и сейчас не требует смены драйвера.
При следующем отключении записать точное время и проверить:

```bash
journalctl -b -k --since '-5 min' --no-pager \
  --grep='NvKmsKapiMemory|NVRM: Xid|Idling display engine|API mismatch|EDID'
```

Наблюдение считается закрытым, если такие строки не повторяются при обычной
работе, переподключении и suspend/resume. Если их новый пакет совпадёт по
времени с blackout, сохранить журнал и только тогда сравнивать 595 NVIDIA-only
с 580 как A/B-тест.

### Новая проблема 2 — отвергнутая раскладка и тяжёлое масштабирование X11

GNOME Shell при входе зарегистрировал точную ошибку:

```text
Failed to read monitors config file
'$HOME/.config/monitors.xml':
Logical monitors not adjacent
```

Ручное редактирование файла оказалось неверным методом: после повторного входа
GNOME снова отклонил файл и применил запасную схему. В ней одновременно были
активны BenQ 150%, AOC 100% и встроенная панель примерно 150%, а X11
framebuffer вырос до `12368×2880`. Это непосредственно объясняло неправильный
масштаб и тяжёлое обновление интерфейса.

В 12:27 схема была применена штатным методом
`org.gnome.Mutter.DisplayConfig.ApplyMonitorsConfig`:

1. метод `verify` подтвердил допустимость схемы;
2. схема временно применена и проверена через `xrandr`;
3. та же схема сохранена методом `persistent`, после чего Mutter сам
   сформировал `~/.config/monitors.xml`.

Повторный вход в 12:40 доказал, что сохранённый файл был **невалидным для
следующего X11-сеанса**: GNOME снова записал `Logical monitors not adjacent`
и включил три дисплея. Причина найдена в исходном коде Mutter 46
`meta-monitor-config-store.c`: XML загружается с X11 layout mode `3`
(`GLOBAL_UI_LOGICAL`), а функция определения размеров не делит ширину режима
на scale для этого значения. Поэтому 4K BenQ занимает в проверяемой раскладке
3840, а не 1920 координатных единиц. Persistent D-Bus при этом сохранил AOC в
`x=1920`, создав файл, который сам загрузчик затем отвергает.

В 12:44 применено исправление для текущего X11-сеанса:

1. в сохранённом XML координата AOC исправлена с `x=1920` на `x=3840`;
2. секция `<disabled>` для `eDP-1-1` сохранена;
3. схема успешно прошла D-Bus `verify`;
4. runtime применён методом `temporary`, чтобы Mutter снова не переписал XML

Для этой конкретной комбинации GNOME 46 + X11 + смешанного масштаба 200%/100%

несовместимую координату `1920`. Рабочая конфигурация — XML с BenQ `x=0`,
`scale=2`, AOC `x=3840`, `scale=1`, eDP в `<disabled>`. Временное

уже подтвердил, что XML загружается самостоятельно, а autostart остаётся no-op.

`x=3840`: GNOME 46 может снова записать несовместимую координату.

**Проверка**

- `~/.local/bin/restore-external-monitor-layout`;

## 2. Подтверждённые сбросы USB-C DisplayPort Alt Mode

### Топология и последовательность сбоя

Оба внешних разъёма обслуживает провайдер NVIDIA:

- AOC 2590G4: HDMI, `DFP-0`;
- BenQ EX2710U: USB-C → DisplayPort, `DFP-2`.

Во время нормального снимка EDID обоих мониторов читались, BenQ работал в
4K60, а его DP `link-status` был `Good`. Значит, соединение умеет нормально
обучаться и работает между сбоями.

Зафиксированы физические исчезновения BenQ примерно на 3–4 секунды:

- 2026-07-25 13:56:01 → восстановление примерно к 13:56:05;
- 2026-07-25 14:06:49 → восстановление примерно к 14:06:53;
- аналогичные последовательности 2026-07-24 около 10:01:08 и 10:02:11.

В каждом случае:

1. Xorg сообщает, что BenQ `DFP-2` отключён.
2. HDMI AOC остаётся отмеченным как подключённый.
3. Xorg временно устанавливает всю схему NVIDIA в `NULL`.
4. Xorg восстанавливает только HDMI.
5. BenQ снова появляется, после чего Xorg восстанавливает полную схему.

Это объясняет, почему могут погаснуть оба монитора, хотя физически пропадает
только USB-C/DP-соединение. Одновременные сообщения ядра:

```text
ucsi_acpi USBC000:00: unknown error 256
ucsi_acpi USBC000:00: con2: failed to register partner alt modes (-5)
```

В разных загрузках также повторяются:

```text
ucsi_acpi USBC000:00: GET_CABLE_PROPERTY failed (-5)
nvidia-modeset: Unable to read EDID for display device DP-0
```

Локальный Type-C-контроллер объявляет активный DisplayPort SVID `ff01`, но
подключённый партнёр в момент проверки не показывает зарегистрированных
альтернативных режимов. Это согласуется с ошибкой UCSI.

События встречаются с 13 июля на ядрах `6.17.0-35`, `6.17.0-40` и
`7.0.0-28`. Они начались до текущего рассогласования библиотек NVIDIA, поэтому
не являются только регрессией ядра 7.0 или следствием обновления драйвера.
В эти моменты не было suspend/resume, PCIe AER, зависания GPU, сообщения
`fallen off bus` или отдельной DRM-ошибки обучения линии.

### Вероятная область неисправности

В порядке практической вероятности:

1. целостность кабеля USB-C → DP или контакта разъёма;
2. DP-вход, прошивка, энергосбережение или автопереключение входа BenQ;
3. USB-C-порт ноутбука, embedded controller, UCSI/ACPI или системная плата;
4. обработка сброса линии драйвером NVIDIA.

NVIDIA участвует в восстановлении раскладки экрана, но ошибки регистрации
партнёра и свойств кабеля происходят на уровне UCSI ниже Xorg.

### Безопасная последовательность A/B-проверок

После исправления версии NVIDIA менять только одну переменную за раз:

1. Отработать обычный сеанс только с HDMI.
2. Отработать сеанс только с BenQ по USB-C/DP.
3. Заменить весь кабель на короткий сертифицированный USB-C → DP 1.4/HBR3
   другого производителя.
4. Перевернуть штекер USB-C. Зависимость от ориентации — сильный признак
   проблемы контакта или линии.
5. Проверить другой DP-capable USB-C-порт ноутбука.
6. Проверить другой USB-C/DP-монитор или адаптер; BenQ подключить к другому
   USB-C/DP-источнику.
7. Временно выбрать консервативные параметры:
   - вместо 4K60 — 2560×1440 60 Гц;
   - Adaptive Sync/FreeSync — off;
   - HDR — off;
   - DSC — off, если доступно;
   - DisplayPort Deep Sleep и автоматический выбор входа — off;
   - временно DP 1.2, если это есть в OSD BenQ.
8. Проверить официальный канал BenQ на наличие прошивки EX2710U.
9. **Выполнено:** Acer BIOS обновлён с V1.21 до V1.26; UCSI/ACPI-сообщения
   сохранились, поэтому продолжить с кабелем, портами и прошивкой BenQ.
   Локальный каталог `fwupd` обновления не предлагает, но Acer может
   распространять его вне LVFS.

Если другой кабель устраняет проблему, виноват исходный кабель. Если один
USB-C-порт стабилен, а другой нет, подозрение падает на порт/линии. Если
несколько исправных кабелей и мониторов сбоят на разных портах, журналы UCSI
обосновывают обращение в Acer. Если сбоит только BenQ, вероятнее его вход или
прошивка.

Не следует начинать с параметров ядра, отключающих UCSI или управление
питанием Type-C: они могут скрыть полезный сигнал и создать проблемы с
зарядкой и hot-plug.

После исправления NVIDIA можно отдельно испытать GNOME Wayland. Он может
мягче обработать hot-plug, чем Xorg с переходом всей раскладки в `NULL`, но не
устранит физический сброс UCSI.

### Реализованное исключение Node.js/Python-проектов

Для установленного Tracker 3.7.1 локальная схема и реализация подтверждают,
что `.trackerignore` — не аналог `.gitignore`: Tracker не читает содержимое
файла. Само наличие marker-файла исключает содержащий его каталог и всё
поддерево. Поэтому glob-списки для `node_modules`, `.venv` и `build` внутри
одного корневого файла были бы ложной конфигурацией.

Проведён manifest-based поиск по `~/Desktop` и `~/PycharmProjects` с
исключением dependency/cache-каталогов. Монорепозитории объединены до
логического корня; nested dependencies, сломанные worktree-контейнеры,
`__MACOSX` и backup-копии не считались самостоятельными проектами.

Созданы 84 marker-файла:

- 49 в `~/Desktop/PycharmProjects`;
- 13 в `~/Desktop/desktop`;
- 22 в `~/PycharmProjects`;
- по структуре: 57 Python, 8 Node.js и 19 смешанных Node.js/Python.

Каждый файл содержит только информационный английский комментарий о marker-
семантике; никаких неработающих pattern-правил нет. Существующие файлы не
перезаписывались. Git-корни тоже получили явный marker: хотя `.git` находится
в системном списке исключающих имён, в старой базе сохранялись и продолжали
обрабатываться их прежние записи.

Фактический результат после создания файлов:

- URI с `/node_modules/` уменьшились примерно с 149 980 до 133 462
  (минус 16 518);
- общий снимок изменился с 243 198 файлов и 40 993 каталогов во время
  первичной диагностики до 169 310 файлов и 25 803 каталогов;
- при итоговом контроле miner использует примерно 41–55 MiB вместо
  наблюдавшихся перед перезапуском 376–416 MiB;
- индексирование завершено, miner простаивает, failed user units отсутствуют;
- `tracker3 status` показывает 315 сохранённых ошибок извлечения. Это
  накопленные исторические записи, а не 315 новых сбоев: после перезапуска
  нет priority-error и повторения crash-сигнатур.

При обработке первой партии исключений старый extractor вошёл в crash-loop:
`TRACKER_IS_RESOURCE` → `munmap_chunk(): invalid pointer` → `SIGABRT` каждые
две секунды. Без удаления базы был перезапущен только пользовательский
`tracker-miner-fs-3.service`; цикл прекратился, повторный перезапуск после
полного набора marker-файлов также чистый.

Ограничение: restart не удалил все старые URI из Git-проектов. Например,
в `adv-cake-vk-mini-app` осталось 2 063 URI. Marker-файлы предотвращают новый
обход этих деревьев и будут учтены при следующем полном построении индекса, но
для немедленного удаления всех старых записей нужен `tracker3 reset
--filesystem` с последующей переиндексацией. Эта операция удаляет и заново
строит поисковую базу, поэтому без отдельного разрешения не выполнялась.

### Рекомендуемый порядок

1. После выполненных исправлений повторить точно известную медленную локальную
   папку и файловый диалог проблемной программы.
2. Перенос проектов из Desktop в `~/Projects` теперь необязателен:
   `.trackerignore` уже исключает найденные корни. Переносить их только для

3. **Выполнено:** добавить `.trackerignore` в подтверждённые корни
   Node.js/Python-проектов; весь проект и generated/dependency-поддеревья
   теперь исключены как единое дерево.
4. **Выполнено:** после изменения области безопасно перезапустить
   `tracker-miner-fs-3`; crash-loop extractor устранён.
5. Только если тормозят папки с медиа, провести A/B-тест миниатюр и подсчёта
   элементов.

Полный reset базы Tracker не обязателен для предотвращения будущей индексации,
но остаётся отдельной опцией для немедленного удаления старых URI. Метаданные
GVfs сбрасывать не нужно. Установленные Nautilus 46.4, GVfs, Tracker и portal
совпадают с доступными кандидатами Ubuntu.

## 7. Память и подтверждённый OOM

2026-07-15 18:19:33–18:19:34:

- Discord вызвал глобальный OOM killer;
- все 8 GiB swap были исчерпаны: `Free swap = 0 kB`;
- был убит процесс VS Code;
- `systemd-journald` пропустил watchdog, перезапустился и переименовал
  системный и пользовательский журналы как corrupted/unclean.

Это настоящий общесистемный случай зависания, а не просто занятый файловый
кэш.

При первичном снимке было занято 5,5 GiB swap. Параллельные чтения больших
журналов во время аудита вытеснили дополнительные неактивные страницы:
показатель вырос сначала до 7,6 GiB, затем почти до 8,0 GiB. При этом
доступно 13–14 GiB RAM, PSI равен нулю, текущего I/O wait и swap I/O нет.
После рекомендуемой перезагрузки этот диагностически усиленный остаток
очистится естественно.

Среди заметных потребителей swap/памяти были долгоживущие Python/tooling
services, GNOME Shell, Telegram, Celery/Airflow workers, VS Code, Chrome,
пользовательские AI/MCP-службы и контейнеры. В одном снимке GNOME Shell имел
около 310 MiB в swap, что способно дать задержку при первом обращении даже без
текущего thrashing.

Рекомендации:

1. Закрывать устаревшие browser/IDE/Electron/development-процессы.
2. Останавливать неиспользуемые Docker stacks.
3. Задать разумные memory limits постоянным контейнерам и worker pools.
4. Перевести тяжёлые пользовательские службы на запуск по требованию.
5. Во время воспроизведения смотреть `free -h` и
   `/proc/pressure/memory`.
6. Если такая нагрузка действительно штатна и не уменьшается, рассмотреть
   увеличение RAM.

Простое увеличение дискового swap может превратить OOM-остановку в более
долгое интерактивное зависание. zram можно рассматривать как отдельный
последующий эксперимент, но не как часть текущей диагностики.

После согласования NVIDIA/NVML температура GPU снова доступна: на контрольных
снимках она составляла 62–64°C при 6–13% загрузки GPU и примерно
1,7 GiB занятой VRAM. Это не аварийная температура; показатель динамический и
не является полноценным idle-тестом.

После перезагрузки:

1. Оставить ноутбук на десять минут без рабочей нагрузки.
2. Выбрать balanced profile и измерить idle.
3. Проверить обычную рабочую нагрузку.
4. Если idle остаётся выше примерно 65–70°C или умеренная работа сразу
   поднимает температуру к 90–95°C с throttling, проверить вентиляцию,
   вентиляторы и рассмотреть чистку/сервис.

NVMe показывали примерно 58°C для занятого системного диска и 46°C для
второго, ниже порогов warning/critical.

## Решение и проверка по каждой проблеме

Ниже приведены отдельные runbook-проверки. Их следует выполнять по порядку:
раскладка экранов и NVIDIA-only уже исправлены и проверены. Теперь сначала
наблюдать текущую 595, затем отдельно изолировать USB-C/DP и повторить сценарий
Nautilus. Откат 595 → 580 оставлен только как резерв при новом Xid. Очистку,
другие обновления и отключение необязательных служб выполнять отдельно, чтобы
было понятно, какое действие помогло.

Для каждого теста полезно записывать время начала, исходное состояние,
выполненное действие и результат. Команды, которые удаляют данные или меняют
автозапуск, выполнялись только по отдельным запросам и перечислены в отчёте;
остальные команды в runbook остаются рекомендациями.

### Проблема 1 — два Xid 31 в PRIME on-demand; текущая 595 NVIDIA-only

**Решение**

1. Рассогласование версий уже исправлено: вся загруженная ветка равна 595.84.
2. Именно две загрузки в режиме PRIME on-demand дали `NVRM Xid 31`, а первая
   также дала display-engine timeout.
3. Переход на `prime-select nvidia` уже выполнен. С 12:09 до 13:25 в
   NVIDIA-only нет новых Xid, API mismatch или display-engine timeout.
4. Команды ниже — только резервный откат на 580, если Xid повторится в
   NVIDIA-only; сейчас их выполнять не нужно:

```bash
sudo apt install nvidia-driver-580-open
dpkg -s nvidia-driver-580-open nvidia-dkms-580-open
dkms status
modinfo -F version nvidia
sudo reboot
```

**Проверка текущей NVIDIA-only-загрузки**

```bash
nvidia-smi
cat /proc/driver/nvidia/version
modinfo -F version nvidia
systemctl --failed --no-pager
journalctl -b -k --no-pager \
  --grep='API mismatch|Unpatched return thunk|NVRM: Xid|Idling display engine'
```

**Проблема исправлена, если**

- `nvidia-smi` показывает GPU без ошибки NVML;
- загруженный модуль, файл модуля и NVML показывают одну версию `595.84`;
- `nvidia-cdi-refresh.service`/`.path` не находятся в failed;
- в новой загрузке нет новых `API mismatch`, Xid 31 и display-engine timeout;
- Ollama и другие GPU-клиенты больше не сообщают timeout обнаружения GPU.

**Проблема не исправлена, если**

- версии после перезагрузки всё ещё различаются;
- `nvidia-smi` по-прежнему не запускается;
- CDI снова падает либо появляются API mismatch, Xid или display timeout.

Если после перезагрузки графическая сессия не поднялась, войти в TTY через
`Ctrl+Alt+F3`, сохранить `dkms status`, `journalctl -b -k` и вывод
`nvidia-smi`. Не использовать установщик NVIDIA `.run` и не переходить сразу
на нерекомендованную ветку 610. Откат на 580 рассматривать только после
сохранения журнала повторного Xid в NVIDIA-only.

### Проблема 2 — периодическое отключение USB-C/DisplayPort и мигание HDMI

Ветка NVIDIA и раскладка уже стабилизированы на контрольном интервале, поэтому
теперь эту проверку можно проводить отдельно. GPU faults относились к двум
PRIME on-demand-загрузкам и не повторились в NVIDIA-only.

**Решение и A/B-последовательность**

1. Один рабочий сеанс использовать только HDMI.
2. Следующий сопоставимый сеанс — только BenQ по USB-C/DP.
3. Заменить весь кабель на короткий сертифицированный USB-C → DP 1.4/HBR3.
4. Отдельно проверить другую ориентацию USB-C и второй DP-capable USB-C-порт.
5. На BenQ временно отключить Adaptive Sync, HDR, Deep Sleep, автоматический
   выбор входа и DSC, если настройка доступна; проверить 2560×1440 60 Гц или
   DP 1.2.
6. Проверить BenQ с другим источником и ноутбук с другим DP-монитором.
7. Проверить официальный канал Acer для BIOS/EC и BenQ для прошивки
   монитора.

Во время каждого отдельного теста:

```bash
journalctl -kf -o short-iso | grep --line-buffered -Ei \
  'ucsi|typec|displayport|nvidia|NVRM|drm|EDID|hotplug'
```

После события:

```bash
journalctl -b -k --since 'YYYY-MM-DD HH:MM:SS' --until 'YYYY-MM-DD HH:MM:SS'
```

Вместо шаблонов времени нужно подставить интервал примерно за минуту до и
после blackout.

**Проблема исправлена, если**

- в нескольких обычных рабочих сеансах BenQ ни разу физически не исчезает;
- нет новых `GET_CABLE_PROPERTY failed`, `failed to register partner alt
  modes`, EDID failure и последовательности disconnect/reconnect;
- HDMI не мигает вслед за перестроением всей схемы NVIDIA.

**Как интерпретировать неудачу**

- новый кабель решил проблему — заменить исходный кабель;
- один порт стабилен, другой нет — вероятна проблема порта/линий ноутбука;
- BenQ сбоит с разными источниками — вероятны монитор, его DP-вход или
  прошивка;
- несколько кабелей и мониторов сбоят на обоих портах — передать Acer точные
  парные timestamps UCSI/Xorg и результаты A/B-тестов;
- физический disconnect исчез, но HDMI всё ещё мигает — отдельно исследовать
  Xorg/NVIDIA и сравнить GNOME Wayland.

### Проблема 3 — медленные папки Nautilus и файловые диалоги

Здесь три возможных вклада: текущая ошибка NVIDIA, гонки быстро меняющихся
файлов и избыточная индексация деревьев разработки.

**Решение**

1. После исправления NVIDIA десять раз открыть одну и ту же известную
   проблемную локальную папку и тот же файловый диалог.
2. **Выполнено локальным исключением:** 84 подтверждённых Node.js/Python-
   проекта получили корневой `.trackerignore`; перенос в `~/Projects` теперь
   не обязателен для снижения нагрузки Tracker.
3. Marker в корне исключает сразу исходники, `node_modules`, `.venv`/`venv`,
   build/output, cache и `__pycache__`; содержимое `.trackerignore` Tracker не
   интерпретирует как шаблоны.
4. **Выполнено:** `tracker-miner-fs-3` безопасно перезапущен без удаления
   базы; crash-loop прекратился, индексирование завершено.
5. Только для медленных каталогов с медиа провести отдельный A/B-тест
   миниатюр.

**Контроль до и после**

```bash
tracker3 status
time gio list '/ПУТЬ/К/ПРОБЛЕМНОЙ/ПАПКЕ' >/dev/null
journalctl --user -b --since 'YYYY-MM-DD HH:MM:SS' \
  --grep='Attempted to add a non-existent file to the view|tracker|extractor'
```

Для GUI-теста использовать одну папку, один режим представления и одинаковый
набор работающих приложений. Записать время каждого из десяти открытий и
наличие полной остановки интерфейса.

**Проблема исправлена, если**

- десять повторных открытий проходят без длительного зависания интерфейса;
- файловые диалоги той же программы появляются стабильно;
- после сужения индексации нет нового большого потока Nautilus race warnings
  и Tracker extractor failures из dependency/venv-деревьев;
- `gio list` остаётся быстрым, а GUI больше не отстаёт от него на секунды.

**Проблема не исправлена, если**

- локальная папка по-прежнему зависает после исправления NVIDIA и остановки
  генераторов файлов;
- `gio list` быстрый, но только окно Nautilus зависает;
- проблема повторяется в новой пустой папке.

Тогда следует зафиксировать точный timestamp, текущую папку, число элементов,
тип файлов, состояние thumbnails и журнал user-session за этот интервал.
Сбрасывать базу Tracker или удалять данные GVfs до этого не нужно.

### Проблема 4 — исторически почти полный swap и риск повторного OOM

**Решение**

1. Перезагрузка уже очистила диагностически усиленный остаток swap: на
   итоговом контроле занято `0 B` из 8 GiB.
2. Закрывать старые окна Chrome/VS Code/Electron и неиспользуемые worker
   processes.
3. Останавливать неиспользуемые Docker stacks.
4. Установить memory limits для постоянных контейнеров и worker pools.
5. Перевести ненужные постоянно Headroom/Ollama/MCP-службы на запуск по
   требованию.
6. Сейчас `swapoff` не требуется; если swap снова почти заполнится, не
   отключать его до выяснения текущего давления памяти.

**Проверка во время обычной работы и в момент задержки**

```bash
free -h
vmstat 1
cat /proc/pressure/memory
cat /proc/pressure/io
oomctl --no-pager
journalctl -b -k --no-pager \
  --grep='Out of memory|oom-kill|Killed process|systemd-oomd'
```

`vmstat 1` остановить через 30–60 секунд с помощью `Ctrl+C`.

**Проблема считается управляемой, если**

- в течение нескольких обычных рабочих дней нет OOM kill;
- во время интерактивной работы `si`/`so` не идут непрерывно, memory PSI
  `full` не растёт длительными сериями;
- доступная память не падает к нулю при запуске штатной нагрузки;
- swap может быть занят холодными страницами, но не вызывает постоянного
  I/O и задержек.

Если OOM повторяется, нужно сопоставить timestamp с cgroup/process,
остановить или ограничить конкретного потребителя. Увеличение swap без
снижения нагрузки не считается доказанным исправлением.

### Проблема 10 — высокие температуры и thermal throttling под нагрузкой

**Решение**

1. После перезагрузки выбрать balanced profile:

```bash
powerprofilesctl set balanced
```

2. Дать ноутбуку десять минут без сборок, моделей, контейнерных задач и
   тяжёлых browser/IDE-процессов.
3. Проверить свободный проход воздуха и фактическую работу вентиляторов.
4. Затем повторить обычную, а не синтетическую рабочую нагрузку.
5. Если idle остаётся горячим, провести физическую чистку/сервис; не менять
   thermal limits вслепую.

**Проверка**

После установки `lm-sensors` в отдельное время удобен `watch -n 2 sensors`.
Без него доступны thermal zones в `/sys/class/thermal/`. Также:

```bash
powerprofilesctl get
journalctl -b -k --no-pager --grep='thermal|throttl|critical temperature'
```

**Охлаждение выглядит исправным, если**

- в balanced idle температура устойчиво ниже ориентировочных 65–70°C;
- обычная умеренная работа не приводит сразу к устойчивым 90–95°C;
- нет thermal-critical shutdown и постоянного throttling при лёгкой
  нагрузке.

Краткий пик около 90°C под тяжёлой нагрузкой сам по себе не доказывает
неисправность. Важны температура в idle, длительность пика и throttling при
обычной работе.

Раскладка мониторов восстановлена без смены или отката драйвера. Сейчас

До физического перезапуска BenQ коннектор `DP-1` был подключён, но система

```text
Производитель: NVT
```

Ожидаемый EDID сохранённого профиля:

```text
Производитель: BNQ
```

Mutter сопоставляет профиль не только по разъёму, но и по EDID. Поэтому при
ложном NOVATEK EDID GNOME объективно не мог применить профиль BenQ: требуемого

правильно завершился сообщением:

```text
Could not restore the two-monitor layout after 30 attempts
```

Это был не сброс содержимого `monitors.xml`, не ошибка координат и не
доказанный дефект NVIDIA 595.84.

### Выполненное восстановление

1. Пока EDID оставался неправильным, через Mutter D-Bus временно применена
   безопасная схема `DP-1 1920×1080 + HDMI-0 1920×1080`; встроенный экран
   выключен.
2. Временная схема не сохранялась постоянно и не меняла правильный
   `monitors.xml`.
3. BenQ выключен, отключён от питания примерно на 30 секунд, а
   USB-C→DisplayPort кабель переподключён с обеих сторон.
4. После включения монитор снова предоставил 3840×2160, и штатный профиль
   применился автоматически.
5. Скрипт `~/.local/bin/restore-external-monitor-layout` обновлён:
   - до 30 раз пытается вернуть штатный BenQ 4K/200% профиль;
   - если 4K EDID отсутствует, но оба внешних экрана доступны в 1080p,
     применяет только временную резервную схему;
   - в резервной схеме оставляет два внешних монитора, выключает eDP и пишет
     предупреждение о недоступном BenQ EDID;
   - не сохраняет ложный NOVATEK профиль в `monitors.xml`.


Дополнительно подтверждено:

- `HDMI-0 connected 3840x2160+3840+0` в X11 framebuffer;

На момент проверки симптом устранён. P03 считается повторно решённой.
Аппаратно-протокольная P04/P16 остаётся незакрытой, поскольку полный power

### Решение при повторении

1. Сразу сохранить текущее состояние, не открывая настройки дисплеев:

   ```bash
   xrandr --query
   journalctl -b -k --since '-5 min' --no-pager \
     --grep='EDID|GET_CABLE_PROPERTY|partner alt modes|NvKmsKapiMemory|NVRM: Xid'
   ```

2. Если у `DP-1` отсутствует 3840×2160, выполнить полный power cycle BenQ:
   выключить, обесточить на 30 секунд, переподключить кабель с обеих сторон,
   выбрать вход DisplayPort.
3. Запустить:

   ```bash
   ~/.local/bin/restore-external-monitor-layout
   ```

4. Если сбой повторится, первым A/B-тестом заменить USB-C→DisplayPort кабель
   на сертифицированный для 4K/60 или выше. Затем повторить тест на другом
   USB-C-порту.
5. Если ложный NOVATEK EDID появляется с другим кабелем на обоих портах,
   проверить доступную прошивку BenQ и диагностировать USB-C/UCSI/разъём
   ноутбука либо DisplayPort-вход монитора в сервисе.

### Критерии окончательного закрытия

Проблему USB-C/DP можно считать решённой только после:

- десяти успешных холодных включений и переподключений;
- нескольких suspend/resume;
- не менее семи дней обычной работы;
- отсутствия NOVATEK EDID, blackout и совпадающих по времени UCSI alt-mode
  ошибок.

Откатывать NVIDIA 595.84 только из-за этого случая не следует. Вернуться к
A/B-тесту драйвера имеет смысл лишь при новом `NVRM: Xid`, `API mismatch` или
воспроизводимом NVIDIA display timeout.

## Adopted Requirements And Deliberate Limits

1. **Separate durable definitions from executions.** Use stable project/case/suite identity, identifiable revisions and results pinned to the version and environment actually checked. A rename is not a new case. Preserve history and retire obsolete definitions rather than deleting linked results. Immutable revision preservation is a requirement of this workflow, not a guarantee inferred from TestRail's history fields.
2. **Search metadata before fetching case bodies.** Use bounded previews, relevant filters and exact retrieval, with explicit complete enumeration for full regression. Do not prescribe TestRail's page size, numeric IDs, centralized service or index implementation. A separate count does not establish a consistent snapshot during concurrent edits.
3. **Detect duplicates and conflicting edits.** Search by behavior/source identity before creation; check expected revision before updating authoritative definitions. A title match or timestamp alone cannot establish equivalence or conflict-safe writing. Storage/transaction mechanisms remain planning choices.
4. **Keep automation ownership explicit.** QA recommends candidate cases/suites. Recommendation, the implementation executor's decision and verified permanent automation are different states. A temporary script's successful run does not make a case permanently automated. This role boundary comes from the user, not the vendor documentation.
5. **Define full inventory honestly.** Full regression covers all active project cases in a recorded snapshot, including cases without permanent tests. Every selected case is accounted for as executed or explicitly blocked/not run/inconclusive. Draft/retired/stale records and applicability limits stay visible; neither the first page nor discovered autotest files stand for the whole library.
6. **Schedule by dependencies, shared state and ownership.** Grouping onto one worker is not an arbitrary dependency graph or a cross-job/run resource lock. Validate case dependencies and data/account/stand isolation. Do not import Python, pytest markers, a lock service or a work-stealing algorithm as mandatory architecture.
7. **Admit work using per-host effective RAM budgets.** Account for browser/driver/children, product/stand, already admitted work and OS/unrelated-workload headroom. A remote product can still consume a large local browser budget. CPU-based worker auto-selection, soft reservations and swap are not hard RAM guarantees; an unknown job is not automatically safe at concurrency one. Bounded safe calibration or blocked admission is preferable to invented estimates.
8. **Monitor, stop admissions and collect owned work.** Use native/background execution for resource observation without model polling. Handle pressure, timeouts, OOM, lost stands and cancellation as explicit infrastructure/coverage outcomes; stop only owned work and preserve usable results. Never disable OOM protection or claim safety against arbitrary external host activity. Existing external targets without management authority need honest telemetry limits and an authorized traffic budget, not blind stand provisioning.

## Non-Adopted Architecture And Evidence Claims

No physical layout, database engine, central service, installer, new MCP scenario, container platform, remote-execution backend or framework was chosen. Permanent autotests remain a separate implementation responsibility. No actual stand, memory peak, cleanup behavior, throughput, latency or token saving was measured. The sources are public documentation snapshots; their APIs/commands are not instructions to install or execute anything in this repository.

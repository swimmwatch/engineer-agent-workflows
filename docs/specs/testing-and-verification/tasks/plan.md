## Outcome and MVP boundary

Deliver **two explicitly invoked testing skills and one shared local case/run application**. A user can check a change through QA, preserve reusable cases, repeat a complete regression against frozen revisions, inspect history in a standalone browser UI, and open the actual upstream Allure viewer without confusing a green chart with complete successful testing.

The application is a separate package in this repository. It stores one canonical library per explicitly opened tested project; a URL-only target needs an explicitly owned local library, not whichever directory is current. UI HTTP and agent MCP use the same application/domain/store semantics. The application does not become a test runner, shared team service or the engineering-workflow MCP's business database.

First version: case/suite management and revisions; explicit frozen run scope; identified observations, attempts, attachments and reports; simple UI and basic settings. Deferred: separate Shared Steps, Defects, TestOps-style CI Jobs and custom Dashboards. Native background jobs are still required execution support, not the deferred CI Jobs feature. No permanent SUT autotest authoring/product repair by QA, implicit task completion, new installer, account platform, event bus, architecture DSL or extra token export.

## User flows and ownership

1. **Check a feature or change — `manual-testing`.** The user explicitly invokes QA and identifies the actual target/authority. QA inspects what exists, searches the shared library, reuses or maintains case/suite IDs and expectations, prepares an appropriate manual charter and temporary drivers, then checks the requested behavior. Unknown oracles stay non-ready; failed cases remain reusable definitions with separate failed observations. QA reports product findings and automation recommendations, but does not silently fix the product, add permanent SUT tests or rewrite expectations to get green.
2. **Repeat the library — `regression-testing`.** The user explicitly invokes regression. It obtains every page/body needed to validate one coherent inventory, freezes the full active required set by default or an explicitly labeled subset, and executes that scope. Active draft/stale cases stay blocked in the denominator; retired exclusions and overlaps/variants are explicit. Required native Prepare work creates meaningful batch handoffs; root-owned native jobs perform the work; native Collect/assessment accounts for every terminal job, attempt, output and gap. A first search page, a count or mapped automation alone cannot certify full regression.
3. **Inspect and maintain state without an agent — standalone UI.** The operator explicitly starts the local HTTP application, selects an authorized project/library and completes its browser approval flow. Humans can search/edit/retire cases with revision conflicts visible, inspect frozen runs/history/attachments and manage bounded basic settings. A UI `beginRun` action freezes metadata only: it does not launch SUT actions or native jobs. MCP agents and the UI observe the same revisions; a stale tab cannot save into another project. Neither skill requires an active UI, and standalone UI use does not require an MCP client or AI agent.
4. **Do routine execution efficiently — internal script-batch support.** Prepared temporary scripts perform routine actions, condition waits and prerequisite/resource-aware batch work inside the root's actual native jobs. The proposed P05 “supervisor” means this internal owned execution/monitor/drain code, **not a third skill, always-running service, central daemon or CaseTool execution endpoint**. P04 connects substantive Prepare/Collect work to those root-owned jobs. Native host workflows do reasoning; scripts do repetitive actions and bounded waits; the root retains live ownership and collects every relevant outcome. This is not a scripts-only fallback or an unconditional model-per-case design.
5. **Read a faithful report — upstream Allure.** Saved canonical observations and sanitized evidence feed bounded, identified rendering. The user opens the actual upstream viewer through safe artifact access. Canonical FAILED/INCOMPLETE, earlier FAIL, blocked/not-run/inconclusive reasons, missing outputs and delivery/cleanup gaps remain visible alongside it. Opening an existing ready view never reruns tests or generates data implicitly; failed/missing rendering is not a ready link.

## Shared runtime architecture

**Proposed common decision.** The commitments in this section are proposed for explicit technical agreement, not already accepted. Deliver the separate local testing workspace required by [MT-018–020](docs/specs/testing-and-verification/spec.md#L189-L214) and [MT-025–037](docs/specs/testing-and-verification/spec.md#L259-L384). The workspace owns canonical case/suite revisions, frozen runs and observations, and bounded report-generation lifecycle. Skills consume its public MCP capabilities; they do not carry copied storage implementations or write raw library files. The engineering-workflow MCP remains a different product boundary, not the testing runtime's server, database or authorization provider.

**Binding delivery and dependency choices.** Use `packages/testing-workspace`, npm package `@engineer-agent-workflows/testing-workspace`, and executable name `testing-workspace`. Implement in TypeScript `6.0.3` for Node `>=22.20.0`, with ordinary packaged dependencies rather than a built-ins-only installed-skill restriction. Use `@modelcontextprotocol/server` `2.0.0`; transport checks use `@modelcontextprotocol/client` `2.0.0` and the existing `@types/node` `22.20.1` baseline. Use the existing Ajv `6.15.0` for the future common Draft 7 data/DTO validation when that contract is reconciled; do not add an unused validator in P00 or write a new schema engine. Preserve one authored specification-local data-schema family and package generated copies, not independently editable contracts. Root [workspace/build scripts](package.json#L8-L32), the existing [MCP package](packages/engineer-agent-workflow-mcp/package.json#L18-L41) and its [strict NodeNext configuration](packages/engineer-agent-workflow-mcp/tsconfig.json#L2-L17) establish the repository baseline. A new runtime package is not automatically included in the existing [hard-coded development MCP packaging](scripts/build-dev.mjs#L239-L247); later delivery work must address it explicitly without inventing an installer.

**Binding ownership and dependency direction.** Keep one reusable domain/application/store core inside this package. Pure domain validation owns record and relationship invariants without transport or file effects. Application operations own explicit project/library authority, revision checks, identified retry intent and outcome derivation; the store owns transactional persistence and derived navigation. Both HTTP/UI and stdio-MCP adapters call these same operations rather than reimplement business rules. Dependency direction is adapters → application → domain/store; domain and persistence do not depend on HTTP, UI, host-specific skill namespaces or engineering-workflow business modules. `CaseRuntime` is an illustrative name for application ownership, not a required class or an extra framework. Other private module/helper names remain flexible. No ambient current project, process-readable path, guessed identifier or encoded context becomes permission. Each operation retains its selected project/library and verified authority; a stale tab or another connection cannot retarget it.

**Binding storage choice and invariants.** Recommend and propose SQLite through Node's `node:sqlite`, not a native npm driver or database service. Keep immutable canonical revision/observation data and retained snapshot/navigation references in one per-library database. Publish related state, expected-revision checks and the identified operation receipt in one transaction; reject conflicts instead of losing edits. A saved retry intent distinguishes replay from changed-content reuse and permits exact effect inspection after a lost reply. Pagination pins a retained immutable inventory/navigation generation and reports current drift separately: a short SQLite read transaction alone does not freeze pages across requests. Run selection retains exact case/suite revisions; later definition edits and unrelated observation appends do not change historical meaning or invalidate an available frozen read. Do not hold database transactions across pages, chat turns or user editing. Derived indexes, exports and Allure artifacts are not editable authorities. Schema/layout, journal settings, search details, request/work limits and recovery DTOs are later packet choices, not inherited from the obsolete drafts below.

SQLite's [Node 22.20 API](https://raw.githubusercontent.com/nodejs/node/v22.20.0/doc/api/sqlite.md) is synchronous and marked Active development; its documented busy timeout is not a universal work/cancellation deadline. [SQLite isolation](https://www.sqlite.org/isolation.html) covers separate processes, so shared persistence does not require a daemon. Reads must not silently repair: use read-only access and expose a recovery prerequisite when needed. [Hot-journal recovery](https://www.sqlite.org/lockingv3.html#hot_journal) can write before a read, so writable-open-on-GET is not a read-only implementation. Explicit authorized recovery, safe local database/sidecar access and renderer/artifact publication need later concrete contracts. A database transaction does not atomically cover external attachment files or renderer output. No performance, crash-durability or platform qualification is claimed by this choice.

**Binding process and execution boundary.** Use separate explicitly started HTTP/UI and stdio-MCP processes over the same core and owned library database, not a mandatory central daemon with an MCP proxy. Each process owns its handles and session lifecycle; closing one client must not terminate another process, unrelated clients or native test jobs. No process-global mutable current-library state is shared between requests. The HTTP/UI process will support independent operator use without an active agent, but its `serve` entrypoint, browser-session bootstrap and report-content isolation are later packet choices, not implemented or advertised by P00. Shared authority policy does not erase transport trust boundaries: browser access requires local listener/origin/session protection, and neither browser context nor stdio connection identity alone grants arbitrary project access.

The application records caller-observed native workflow/job/resource facts; it does not execute SUT (system under test) scenarios, provision stands, take over native host orchestration or infer live job ownership from stored handles. A later report coordinator owns bounded renderer work, sanitized inputs, identified generation/retry state and validated ready artifacts; it does not rerun tests to rebuild a report. Use the actual upstream Allure viewer and preserve canonical verdict/completeness separately. Exact Allure version, renderer integration and UI framework remain unselected. P00 registers no Case, Run, Renderer or other custom testing tools and makes no saved-data, UI or report-readiness claim.

**Meaningful alternatives and rationale.** Canonical JSON files with immutable publication/index generations and one current pointer remain a viable text-review alternative. They would replace SQLite transactions with application-owned cooperative locking, multi-file publication and interruption recovery; platform durability becomes more application code. SQLite is recommended for existing transaction/recovery machinery, not an unmeasured speed claim. A mandatory central daemon plus MCP proxy could centralize session and renderer ownership, but adds an always-required service, authenticated IPC/discovery, proxy/server compatibility and restart/shutdown ownership. It does not remove revision checks, receipts or retained snapshots. The proposed direct shared-core architecture avoids that additional mandatory service. These alternatives explain the choice; their old algorithms are not jointly selected sources.

**Binding evidence and verification boundary.** Reuse the existing SDK [stdio startup/close pattern](packages/engineer-agent-workflow-mcp/src/main.ts#L1-L19), [server factory/dispatch pattern](packages/engineer-agent-workflow-mcp/src/server.ts#L103-L155), [Ajv compilation pattern](packages/engineer-agent-workflow-mcp/src/product/schemas.ts#L71-L129) and [isolated package test discovery](scripts/run-tests.mjs#L152-L205), without importing their workflow business state. Implement Linux/Windows/macOS runtime compatibility and stable desktop Chrome/Edge/Firefox/Safari UI compatibility. Development execution evidence is Linux and real Google Chrome only; the other required platforms remain supported and unverified in this cycle, not passed, dropped or additional native completion gates. Source inspection, Node 24 availability and existing unrelated CI matrices do not prove the new runtime or Allure on Node 22.20. Future packets must distinguish implementation support from observed qualification.

## Scope, limits and safety that remain in force

- **One explicit local operator, separate projects.** No guessed path/UUID/encoded context is authority. Browser access needs the finalized local session/origin/CSRF boundary; unsafe roots/attachments and report active content fail closed. P07 currently recommends persistent retirement of BOTH UI/API and report origins, per-artifact isolation and a body-only report ticket. These remain unagreed technical choices, not a specification-prescribed or already accepted architecture; any alternative must preserve the required isolation.
- **Definitions are not results.** Stable IDs and immutable revisions survive rename/retirement. Full regression retains active non-ready cases and every required execution/variant/gap; older failures are not erased by later PASS. A saved receipt, exit zero, a live-phase label or a green report percentage is not proof of complete testing.
- **Bounded coherent data/work.** Use accepted P01/P02/P03 limits/algorithms, not old pre-amendment numbers repeated elsewhere. Retained snapshot pages remain coherent during unrelated appends; touched revisions use current-state compare-and-swap. Bound actual bytes/counts/work and preserve full denominators rather than truncate truth. Cooperative deadlines and synchronous SQLite lock waits are not hard interruption guarantees. The 1,000-case/100-suite fixture is qualification input, not measured customer load or a throughput promise.
- **Owned execution and recovery.** Temporary drivers stay outside SUT production code. Native Prepare/Collect must be substantive and root-owned jobs fully collected; stored PIDs/handles/claims are not current authority. Admission respects dependencies, exclusive resources and the actual local/remote stand/physical-host domain; unknown capacity is not infinite. Cancellation/pressure/interruption drains only owned resources and preserves uncertainty. No age-based lock stealing, foreign port/process kill, automatic replay of non-idempotent work or hidden script-only fallback.
- **Durability/privacy without side effects on reads.** Lost acknowledgment requires exact intent/effect inspection before retry. Reads never initialize, migrate, repair or render. Retain valid identities/history/evidence and a recoverable prior state; missing evidence stays unavailable. Deletion, retention changes, migration/restore, installs/downloads, global client/MCP registration, commits and publication need their own explicit scope. No credentials/private paths/raw personal data in retained cases, artifacts, diagnostics or source.
- **Support is not measured coverage.** Implement Linux/Windows/macOS and stable desktop Google Chrome/Edge/Firefox/Safari. Development native verification is Linux and real Google Chrome only; Chromium is not a Google Chrome pass. Other required environments stay supported and unverified in this cycle, not dropped and not extra native completion gates. CaseTool's Node floor is `>=22.20.0`; Node 24/tool availability does not prove that floor or the upstream renderer there. Tested SUT platforms remain task-dependent, not restricted to the tool's development matrix.

Ten manually retained case versions do not prove frozen evidence. Observed public Cloud/self-hosted price was $39/user/month, not a quote or approved budget. Self-hosting adds PostgreSQL, S3-compatible storage, RabbitMQ, Redis, SMTP and vendor-registry prerequisites. Official guidance uses supported allurectl/CI result upload, not custom internal upload clients; the specific CSV import page said disabled/reworked despite older general copy. **Upstream Report versus case database.** Both Apache-2.0 branches were maintained at the observation: [3.22.1](https://api.github.com/repos/allure-framework/allure3/releases/latest), released 2026-10-23, and [2.46.1](https://api.github.com/repos/allure-framework/allure2/releases/latest), released 2026-09-03. Allure 3 uses Node/npm without Java; Allure 2 documents Java 8+. The pinned 3.22.1 CLI manifest does not establish a minimum Node; upstream dev Node 24.14 and the earlier reported local Node 24.20/SQLite 3.53.4/FTS5 availability do not prove Node 22.20, cross-platform behavior, private paths or crash durability. Do not turn absence of a minimum-engine declaration into compatibility proof.

Input result files, generation and generated HTML are distinct artifacts. Temporary drivers can emit supported result/step/attachment data without writing permanent framework autotests; real observations, stable case/attempt identity and completeness are still required. Arbitrary stdout or generator exit zero is not test success. Sources: [result format](https://allurereport.org/docs/how-it-works-test-result-file.md), [pinned reader](https://raw.githubusercontent.com/allure-framework/allure3/v3.22.1/packages/reader/src/allure2/index.ts), [viewing/single-file output](https://allurereport.org/docs/v3/view-report.md).

- Allure's five statuses cannot replace six canonical case outcomes/three overall verdicts. In 3.22.1 skipped/unknown are excluded from success-rate denominator and a latest retry may dominate display: preserve all required gaps and earlier product FAIL even after later PASS.
- Pinned retry identity uses testCaseId/fullName, non-excluded parameters and environment identity; incoming historyId is legacy metadata. Temporary paths/random names or collisions can break/merge history; use exact stable case/revision/variant/attempt provenance.
- Single-file output can be viewed without a server; multi-file needs HTTP. Generation/history writes and upstream open/serve may create temporary output: they are not read-only browsing. Pinned CLI defaults to all interfaces despite localhost-oriented prose, and its static server provides no authentication. Actual local binding, authorized artifact containment, active-content isolation and owned lifecycle must be supplied, not inferred from a displayed URL.
- Hidden/masked values are not secret removal. Redact inputs/logs/screenshots/attachments before retention/export; hostile active HTML needs the explicit download/isolation boundary, never a mutation-origin shortcut.

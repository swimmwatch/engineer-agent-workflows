## Role in the two skills

When the user explicitly invokes `regression-testing`, the skill takes the required cases from the shared library, prepares temporary test drivers, executes the selected checks and saves their results for Allure. This packet connects those steps using the host's native workflow. It does not create another user-facing skill, case library or permanently running service.

The workflow prepares batches and assesses their collected results. The root keeps ownership of the live background jobs between those stages. P05 supplies the internal script that performs routine actions and waits inside each batch. `manual-testing` uses the same library and may reuse that execution support, while retaining its separate responsibility for investigating changes and maintaining reusable cases. The case-management web application stores and displays cases/results; it does not become the SUT executor.

## Technical proposal

### Outcome and ownership

Recommend one concrete algorithm: substantive native **Prepare** → live **root-owned native batch jobs** → all-terminal **Collect and assess**, with identified repair batches when necessary. This delivers MT-013–017 and MT-022/023 without a scripts-only fallback, no-op workflow wrapper, model per case or model-driven routine-action/wait loop. Temporary drivers remain outside SUT source; persistent generic collection support is allowed. Neither skill writes permanent SUT tests or repairs product code.

Inherit the accepted separate TypeScript/Node testing workspace, SQLite case persistence and public MCP access. `CaseRuntime` records caller-observed workflow/job/resource facts and coordinates bounded report rendering; it is not a SUT executor, live resource authority or host workflow bridge. Standalone QA/regression requires compatible CASE TOOL capabilities, not engineering-workflow MCP or an installed planning skill. Packet conformance additionally uses its existing read-only specification/agreement checks. Regression consumes frozen definitions; QA owns case maintenance. Both remain explicit-only.

### Selected staged algorithm

1. Preflight discovers actual native schemas, permissions, target/driver tools and bounded output/wait/cancellation paths. Missing support yields an affected `BLOCKED` result; no automatic SDK/plugin/global upgrade, registration, credential use or fallback to a plain command.
2. Native Prepare reads the complete frozen selection and selected exact bodies, preserves active draft/stale/non-ready cases in the denominator, records blockers, constructs the dependency/isolation/resource policy and prepares temporary drivers and expected outputs. It returns an identity-checked handoff, not an unchanged input or a label around pre-existing automation.
3. The root validates that handoff, persists an identified launch intent through CASE TOOL, then starts only prepared root-owned native jobs. It records actual launch IDs and supervisor start evidence. A lost response is reconciled against exact native state/attempt evidence, never by automatic relaunch. The bridge executes the fixed policy; it cannot invent cases, expectations, targets, schedules or repairs.
4. Checkpoint the frozen reference, stage/attempt ledger, job identities, remaining coverage, persistence and cleanup state. Use native pending/notification or a supported blocking wait with no model polling. Ending Prepare does not transfer child ownership. Root/session/process loss requires reconciliation; a saved handle cannot resurrect a job. A healthy waiting batch is not killed merely to end a chat turn.
5. Root collects **every** relevant terminal job, including failed/cancelled/null/out-of-order outcomes, and validates complete bounded artifacts. Only then invoke native Collect/assess. It joins the full denominator, distinguishes product assertions from driver/infrastructure failures and returns report inputs or an identified Prepare-repair handoff. Corrected code gets a new driver digest and attempt; earlier failures survive. Repair never changes the oracle to accept a bug or duplicates uncertain non-idempotent effects.
6. Operation cancellation stops admissions and requests supervisor graceful drain before any native escalation; collect all mapped owned work. Stopping a workflow stage is not cancellation of independent root jobs. Late results remain attributed to their original attempt and cannot reopen a sealed epoch or count twice. Unresolved cleanup, persistence, output or prior effects keeps the run incomplete. Product failure still takes verdict precedence, with gaps visible.

A single workflow with batch-owning children is a meaningful alternative only for fully bounded batches whose entire launch/wait/collect/drain fits a qualified child lifetime. It is not selected: the inspected Harness child can settle/dispose its jobs, and returning a live child job ID transfers no authority. Root-owned staged execution avoids that trap at the cost of explicit handoffs and separate operation cancellation. No fallback switches algorithms silently.

### Identities, payloads and callbacks

`StageEnvelope` identifies the canonical project/library, run and frozen selection reference/revision; stage (`prepare`, `collect` or `repair`), monotonically advancing stage epoch, prepared policy digest, root native owner/session and expected batch set. Each batch fixes its case-revision/variant execution keys, target/build identity, driver reference/content digest, expected-output set, authority, resource domains and finite execution/cleanup/repair budget. Batch and attempt identities are different: repair increments an attempt and retains its predecessor/reason. Native workflow IDs, agent IDs, job IDs, canonical run IDs and atomic persistence request identities are never interchangeable.

`OwnedExecution` adds the actual native owner, job/executor kind and ID, launch attempt and supervisor process/start epoch. `TerminalBatch` echoes those identities and contains native terminal status, exit/signal/cancellation facts, driver health, every expected case output or explicit missing/blocker reason, bounded evidence references and cleanup state. A terminal native job is not automatically a valid driver run or product pass. Null/failed/cancelled members retain their expected slots; never `filter(Boolean)` them away.

`journal.read` maps to `/definitions/Operation_openRun` → `RunHeadResult` and `Operation_getRunRecord` → `PortionResult`, with `RunGetParams.ref/cursor`; consume every exact portion. `journal.save` maps to `Operation_beginRun`, `Operation_appendObservations`, `Operation_checkpointRun`, `Operation_finalizeRun` → `WriteReceipt`, not guessed storage APIs. All envelopes use `{protocol_version,kind,request_id,operation,library,params}`; `LibrarySelector` contains only project/library IDs, never authority. Append uses `run_id/expected_run_revision/observations` (1–16); checkpoint uses `run_id/expected_run_revision/checkpoint: CheckpointInput`. Consume actual `WriteReceipt.run_revision/saved_refs`; saved acknowledgment is not native execution success. Lost persistence replies use `Operation_inspectOperation` with exact request ID/digest before exact replay or `Operation_recoverOperation`; never confuse this mutation identity with the invocation operation UUID or native job ID.

Bind expected keys to `/definitions/RunSelection` → `executions[]: FrozenExecution`, fields `execution_key/case_ref/variant/target_id/required/readiness/prerequisite_issues`; `Variant` is `environment_key/parameter_key/repetition`. Consume stored execution keys under P03's algorithm, not a second selection/dedup rule. `StageEnvelope` remains transient. Persist launch/attempt/cleanup provenance as `/definitions/ExecutionFact`: native host/nullable owner/session/job IDs, invocation `operation_id`, `stage_id/batch_id`, `attempt_epoch`, nullable `driver_digest`, selected `execution_keys`, `state=launch_intent|started|terminal|unknown`, `terminal_ref` required for terminal, cleanup, `metric_facts: ResourceFact[]` and nonempty `source_refs`. Its attempt epoch is not `Observation.attempt` (1–32). `Observation`, `Checkpoint` and `CheckpointInput` carry at most 64 `execution_facts` and 32 `external_stage_artifacts`; larger ledgers use referenced artifacts, not dropped facts. Checkpoint phases are exactly `pending|running|waiting|interrupted|terminal`, separate from verdict.

Use `/definitions/ExternalStageArtifact` and `ArtifactPageRef` for artifact/source digests and complete cursor-bound page delivery: ≤64 MiB/artifact, page count 1–1024, 1–64 indexed page refs per descriptor. Follow all continuations and validate completeness/identity; a partial descriptor is not the whole ledger. `/definitions/OwnedHandle`, `Reservation`, `ResourceFact` and `ValueFact` persist caller facts only, never live claims. `native.launch/collect/cancel` stay root-owned discovered tools, inaccessible from the workflow VM. Unknown launch effects forbid replay until reconciled; persistence and native launch are not one transaction.

Propose at most **24 KiB UTF-8 per model-facing envelope/page**, **50 complete batch/result metadata references per page**, and **64 KiB diagnostics per batch**; larger bounded artifacts are retrieved by validated references/portions. These are transport/context bounds, not total case, batch or regression-duration limits. Truncation never means complete delivery. Collect/assessment requires the entire expected terminal ledger and every required output; gaps remain explicit. Routine condition waits, pressure sampling and process settlement stay inside the supervisor, not stage agents.
